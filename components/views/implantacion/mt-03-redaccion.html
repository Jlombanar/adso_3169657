Cómo se escribe un buen manual técnico

Aquí sí se usan palabras técnicas, pero con precisión: el lector debe poder hacer el cambio solo con lo que dice el documento.

1
Nombres exactos. Archivos, carpetas, rutas, tablas y variables se escriben tal como están en el código y en formato de código: backend/controllers/heladoController.js, no "el controlador de los helados".
2
Versiones siempre. "Flutter 3.24" o "Node 20", no "la última versión". Con otra versión el proyecto puede no compilar.
3
Un diagrama vale más que tres párrafos. La arquitectura y el modelo de datos se explican primero con una imagen y después con texto.
4
Ejemplos de petición y respuesta. En cada endpoint, un JSON de ejemplo de lo que se envía y lo que se recibe, incluidos los errores (401, 404, 500).
5
Fragmentos cortos de código. Solo las líneas que explican algo importante, con la ruta del archivo arriba. El código completo está en el repositorio.
6
Nunca secretos. Ni contraseñas, ni llaves de Supabase, ni el JWT_SECRET, ni la clave del keystore. El manual puede terminar en manos de cualquiera.

Así no / así sí

❌ Así no✅ Así sí
"El backend guarda los helados.""POST /api/helados valida el token de administrador, sube la imagen a Cloudinary y guarda el registro en la tabla helados de Supabase."
"Instalar las dependencias.""En la carpeta backend/, ejecutar npm install. Requiere Node 20 o superior."
"SUPABASE_KEY=sb_secret_3fA9…""SUPABASE_KEY: llave secret del proyecto. Se obtiene en Supabase → Project Settings → API Keys. Solo va en el backend."
"Si falla, revisar el código.""Si Render responde 502, revisar en Logs que el servidor use process.env.PORT."
🧪
La prueba del manual técnico
Denle el manual y el enlace del repositorio a un compañero de otro equipo. Pídanle que lo haga funcionar en su computador y que agregue un campo nuevo a los helados. Donde se quede pegado, ahí le falta algo al manual.
