¿Qué es Render y qué tipo de servicio usamos?

Render es una plataforma en la nube (PaaS) donde se conecta un repositorio de GitHub y la plataforma construye y ejecuta la aplicación. En el menú New aparecen varios tipos de servicio.

Tipo de servicioPara qué sirve¿Es el nuestro?
Web ServiceAplicación que recibe peticiones HTTP: APIs, sitios con servidor.✅ Sí: nuestro backend Express.
Static SiteSitios HTML/CSS/JS sin servidor (por ejemplo, un frontend web compilado).No para el backend.
Private ServiceServicio accesible solo desde otros servicios internos.No.
Background Worker / Cron JobTareas en segundo plano o programadas.No por ahora.
Postgres / Key ValueBases de datos administradas por Render.No: usamos Supabase.
⚠️
Limitaciones del plan gratuito (según la documentación de Render)
• El servicio se duerme tras 15 minutos sin tráfico y tarda cerca de un minuto en despertar en la siguiente petición.
• El sistema de archivos es efímero: lo que se guarde en disco se pierde al reiniciar o redesplegar. Por eso las imágenes van en Cloudinary y no en la carpeta uploads.
• No permite tráfico saliente por los puertos SMTP (25, 465, 587). Por eso el correo se envía con la API de Brevo y no con Nodemailer/Gmail.
• Hay 750 horas gratuitas al mes por workspace. No se recomienda para producción.

Fuente: render.com/docs/free

PASO 1 · PREPARAR EL BACKEND

Antes de subir: dejar el proyecto listo

Render ejecuta npm start y le asigna el puerto por una variable de entorno. Hay tres cosas que revisar.

✍️
El código de esta guía no se puede copiar a propósito: escríbanlo ustedes mismos.
📄 backend/package.json — script start
{ "type": "module", "scripts": { "start": "node server.js", "dev": "nodemon server.js" } }
📄 backend/server.js — usar el puerto que entrega Render
const PORT = process.env.PORT || 3000; app.listen(PORT, () => { console.log(`Servidor corriendo en el puerto ${PORT}`); });
📄 .gitignore (en la raíz o en backend/)
node_modules/ .env uploads/
1
start vs dev: en el servidor no se usa nodemon; Render ejecuta npm start.
2
process.env.PORT: Render decide el puerto; si se deja fijo en 3000 el servicio puede no responder.
3
.gitignore: el .env y node_modules nunca se suben. Verifiquen con git status antes de hacer push.
4
Subir a GitHub: git add . → git commit -m "listo para render" → git push origin main.
PASO 2 · CREAR EL WEB SERVICE

Configuración en el panel de Render

En el panel: New → Web Service, y conectar el repositorio de GitHub del proyecto.

Campo en RenderValorExplicación
Sourceusuario-github / helados_mimosRepositorio de GitHub desde donde Render descarga el código.
BranchmainRama que se construye y despliega. Cada push a esta rama redespliega automáticamente.
Root DirectorybackendComo el repositorio tiene backend y frontend (monorepo), se le indica en qué carpeta está el servidor. Los cambios fuera de ella no disparan despliegue.
Build Commandnpm install --legacy-peer-depsInstala las dependencias. La opción --legacy-peer-deps evita errores por conflictos de versiones entre paquetes.
Pre-Deploy Command(vacío)Opcional: migraciones o tareas previas al arranque. No lo necesitamos.
Start Commandnpm startComando que arranca el servidor en cada despliegue.
Instance TypeFreePlan gratuito para aprendizaje, con las limitaciones vistas arriba.
1
Iniciar sesión en Render con GitHub y autorizar el acceso al repositorio.
🔗 Ir al panel de Render
2
Abrir el menú New, elegir Web Service y seleccionar el repositorio.
3
En la sección Build, completar Branch, Root Directory y Build Command según la tabla.
4
En la sección Deploy, escribir el Start Command npm start.
5
Agregar las variables de entorno (siguiente paso) antes de crear el servicio, y entonces presionar Deploy Web Service.
PASO 3 · VARIABLES DE ENTORNO (.env)

Cargar el .env en Render

El archivo .env no se sube a GitHub, así que Render no lo tiene. Cada variable se registra en el panel, en Environment → Add Environment Variable (Key y Value).

🔐
Reglas de oro
• Los nombres (Key) deben ser idénticos a los que el código lee con process.env.NOMBRE.
• Los valores se escriben sin comillas ni espacios sobrantes.
• Nunca pegar llaves reales en chats, capturas, documentos ni repositorios. Si una llave se expone, hay que regenerarla.
• Si agregan o cambian una variable después, hay que redesplegar para que el servidor la tome.
PASO 4 · DESPLEGAR Y PROBAR

Verificar que el servidor quedó arriba

1
Render muestra los Logs del build: debe terminar con "Build successful" y luego imprimir el mensaje de arranque del servidor.
2
En la parte superior aparece la URL pública, con la forma https://nombre-del-servicio.onrender.com. Estado Live = en línea.
3
En Postman, cambien http://localhost:3000 por la URL de Render y prueben, por ejemplo, GET https://nombre-del-servicio.onrender.com/api/productos.
4
Prueben también login y crear producto con imagen (Cloudinary) para confirmar que todas las variables quedaron bien.
5
Si la primera petición tarda cerca de un minuto, no es un error: es el servicio gratuito despertando.
🔁
Despliegue continuo
Cada vez que hagan git push a la rama main (con cambios dentro de backend/), Render vuelve a construir y desplegar solo.
